## 2. 项目设计路线速读

Chronovita 不是普通 AI 问答网站，也不是只放视频和地图的资料库。它的设计路线是把一节历史课拆成四个可交互学习动作：

```text
看：地图、课文、视频、关键词，建立历史图景
练：saga / sandbox，把历史情境变成可推演的抉择局
问：专家 / 历史人物双模态智能体，解释疑惑与时代视角
创：知识画板和智能笔记，把学习结果沉淀为个人知识谱系
```

开发时要始终保留这个闭环。新增功能如果无法归入“看、练、问、创”中的某一层，通常应先回到产品规划讨论，而不是直接加页面。

## 3. 技术路径

当前项目采用开发期单体架构，优先保证本地可演示、可快速迭代、可逐步迁移：

```text
React + Vite + TypeScript + Ant Design 前端
        |
FastAPI + Pydantic 后端
        |
services 业务服务层
        |
SQLite KV 持久化 + 文件化课程素材 + LLM 适配层
```

中长期演进路径：

| 阶段 | 技术方向 |
| --- | --- |
| 当前 | SQLite、mock/DeepSeek/OpenAI 兼容 LLM、本地课程数据、单用户或轻量演示 |
| 近期 | 管理员内容编辑器、课程文件封存、内容审校状态、关键路径测试 |
| 中期 | Postgres、对象存储或 Git 化内容仓库、教师后台、班级与作业 |
| 长期 | 向量库/RAG、内容版本审计、多模型路由、生产部署与权限治理 |

## 4. 管理员内容生产与发布

当前实现是单管理员、文件驱动的内容生产后台，不是生产级多用户 CMS。`LessonContentPackage.status` 只描述 `draft|sealed` 制品状态；审校和学生可见性由独立工作流与课程发布清单决定。**封存不等于发布**。

```text
课程草稿 -> 校验 -> 审校 -> 课程封存 ----+
关卡表单 -> 校验 -> 关卡封存 ------------+-> 选择保留/更新/清空绑定 -> 发布 V2 整课快照
                                                                          |
学生课程 API + 正式游戏目录 <- 同一活动指针 <- 同一课程发布清单 <---------+
                                              ^
                                              └---------- 回滚生成新快照
```

| 层 | 当前实现 |
| --- | --- |
| 鉴权 | `/api/v1/admin/content` 使用临时 admin token，支持 Bearer 与 `X-Admin-Token`；配置无默认通用口令，一键启动脚本为本次进程生成随机 token；审计操作者固定取认证后的 `CHRONO_ADMIN_ACTOR`，请求体中的显示名称不能伪造审计身份 |
| 编辑制品 | `LessonContentPackage` 禁止未知字段，保存到 `content/drafts/{lesson_id}.json`；重复保存相同正文不会撤销已有审校状态，实质内容变化会清除旧校验与批准 |
| 最低校验 | `validate_package()` 阻止空正文、无关键词释义、无人物摘要、无 facts 或无可追溯资料的内容进入审校；AI persona、问答点、地图点和互动目标当前为警告 |
| 审校记录 | `content/workflows/{lesson_id}.json` 保存状态、revision、校验报告和连续事件历史；保存、校验、提交、退回、通过、封存、发布和回滚均留操作者与时间 |
| 封存制品 | `content/sealed/{lesson_id}-vNNN.json` 不可覆盖，记录版本、时间、操作者和 SHA-256；只有 `approved` 的当前草稿可以封存 |
| V1 制品 | 发布时通过 `course_package_from_legacy()` 生成 `content/packages/v1/{lesson_id}-vNNN.json` 兼容制品；V2 再把课程与精确 `scenario_refs` 绑定为 `content/runtime/v1/course-packages/.../vNNN-{checksum}.json` |
| 关卡暂存 | `POST /api/v1/admin/content/runtime-scenarios` 只接受 checksum 正确的 sealed `ScenarioTemplateV1`，按内容寻址写入 `content/runtime/v1/scenarios/`；暂存文件存在不表示已发布 |
| 关卡作者草稿 | `services/content/scenario_authoring.py` 使用 `scenario-author-draft/v1` 保存教师表单数据到 `content/scenario-drafts/{scenario_id}.json`；草稿允许存在尚未通过跨引用校验的规则，revision 乐观锁拒绝陈旧覆盖 |
| 关卡校验与封存 | 校验把作者草稿编译为严格 `ScenarioTemplateV1` 并返回逐字段问题；封存由服务端生成版本、认证操作者、时间与 checksum，再复用既有内容寻址暂存层；相同语义内容重复封存幂等返回原版本 |
| 教师联合发布 | `/admin/content` 的课程“审校与发布”区显示当前线上关卡，并提供“保留现状 / 更新绑定 / 清空绑定”三态；更新时从当前课程和课时的 sealed 关卡中选择精确版本，同一关卡 ID 只能选一个版本，非空绑定必须选择唯一主关卡 |
| 发布清单 | `content/releases/manifests/{course_id}/{release_id}.json` 是不可变整课快照；`content/releases/active/{course_id}.json` 是原子替换的活动指针，也是学生可见性的唯一提交点 |
| 发布事务 | `content/releases/transactions/{course_id}.json` 在指针切换前记录旧/新工作流投影；API 启动时依据活动指针自动完成或回滚，成功后立即删除 |
| 学生读取 | `services/courses` 读取 active V1/V2 清单指定的课程包，V2 课时公开最小 `scenario_refs` 与唯一 `primary_scenario_id`；`services/game_runtime` 从同一 active V2 清单读取 `audience=published` 关卡，正式启动必须携带课时响应形成的完整 release pin；校验失败时 API 返回稳定 `503`，不回退到未发布内容 |
| 回滚 | 回滚不改写历史文件，而是先复验目标课程包、全部关卡及 `RuntimeBundleV1`，再复制为新的 V2 release 并移动活动指针；不同课程互不连带回滚 |

关键管理接口：

| 方法与路径 | 前置状态 | 结果 |
| --- | --- | --- |
| `POST /api/v1/admin/content/drafts` | 任意可校验草稿 | 原子保存草稿，建立或刷新工作流 |
| `POST /drafts/{lesson_id}/validate` | 已保存草稿 | 只写入最低内容校验报告，不改变任何学生可见内容或 release |
| `POST /drafts/{lesson_id}/submit-review` | `validated|changes_requested` | 进入 `in_review` |
| `POST /drafts/{lesson_id}/review` | `in_review` | `approve` 进入 `approved`；`changes_requested` 必须附退回说明 |
| `POST /drafts/{lesson_id}/seal` | `approved` | 生成不可变 sealed 版本，学生端仍保持原发布内容 |
| `GET /runtime-scenarios` | 管理员 | 列出已登记的 sealed 关卡及其精确版本、checksum 和内容寻址描述符 |
| `GET /runtime-scenarios/{scenario_id}/versions/{scenario_version}` | 管理员；查询参数提供 `course_id + lesson_id + scenario_checksum` | 按完整制品身份复验并返回 sealed `ScenarioTemplateV1` 与描述符，供刷新后预览和 1:1 导出；不采用“同 ID 最新版本”回退 |
| `GET /runtime-scenarios/{scenario_id}/versions/{scenario_version}/file` | 管理员；查询参数同上 | 复验完整制品身份与 checksum 后直接返回不可变封存文件的原始字节；前端不得重新序列化后冒充 1:1 导出 |
| `POST /runtime-scenarios` | sealed 且 checksum 正确的 `ScenarioTemplateV1` | 登记不可变关卡制品，不改变学生或游戏目录可见性 |
| `GET /scenario-drafts/template` | 管理员 | 返回可直接编辑的作者草稿样板；样板历史文字是教师待填提示，不是正式课程内容 |
| `GET/POST /scenario-drafts` | 管理员 | 列表或保存服务器关卡草稿；`PUT /scenario-drafts/{scenario_id}` 使用 revision 防止陈旧页面覆盖新内容 |
| `POST /scenario-drafts/{scenario_id}/validate` | 已保存关卡草稿 | 编译严格契约并返回字段路径、错误代码和消息，不写 sealed 制品 |
| `POST /scenario-drafts/{scenario_id}/seal` | 校验通过的关卡草稿 | 自动生成不可变版本与 checksum 并登记到 runtime 暂存层；不改变学生端可见性 |
| `POST /sealed/{lesson_id}/versions/{version}/publish` | 当前工作流的 sealed 版本 | 生成整课 V2 release 并切换活动指针；`scenarios=null` 沿用、`[]` 解除、显式列表替换绑定，非空列表必须且只能有一个 `primary` |
| `POST /releases/{course_id}/bootstrap-legacy` | 无活动 release；显式列出 `lesson_id + content_version` | 对白名单旧 sealed 逐份校验后建立首个受管 release；不允许目录扫描自动发布 |
| `POST /releases/{course_id}/rollback` | 已有活动 release | 以历史 release 为目标生成新的回滚快照 |

所有 signed metadata、sealed、课程包和关卡制品在读取时都会复算 checksum，并校验规范路径、课程 ID、课时 ID、稳定制品 ID 与版本身份。单文件写入使用同目录临时文件、`flush + fsync` 和原子替换；不可变文件使用原子硬链接实现“只创建、不覆盖”。发布与回滚先复验快照内 sealed 源、内容寻址课程包、全部关卡及 `RuntimeBundleV1`，并检查跨课程 `lesson_id` 与 published `scenario_id` 唯一性，再完成 manifest 和整门课程的工作流投影，最后才原子替换 active pointer；接口返回失败时课程与游戏目录都仍读取原 release。发布前记录活动指针身份，两个并发请求从同一旧指针出发时只有一方可提交，另一方稳定冲突并要求重试。`content/releases/transactions/` 保存短生命周期恢复日志，API 重启时按活动指针完成或回滚中断事务；可重入的全局工作流文件锁串行化本机多 worker 的保存、审校、封存和发布操作。生产集群跨主机部署时仍应迁移到支持事务/CAS 的数据库或对象存储。

兼容规则：学生课程服务不扫描 `content/sealed` 猜测最新版本。历史 sealed 只有通过管理员 `bootstrap-legacy` 接口显式列出课时与版本、通过最低发布校验并生成 active pointer 后才可见；普通草稿校验和封存都不会触发迁移。内置 Python 课程继续作为没有发布覆盖时的回退。

### 4.1 V1 课程运行契约

`ARCH-001` 已在不改变现有内容接口、saga 和 sandbox 行为的前提下建立规范 V1 对象：

| 对象 | Python 模型 | 主要职责 |
| --- | --- | --- |
| 课程包 | `services.contracts.CoursePackageV1` | 表示一节可封存课时，保留现有课程字段并为人物、关键词、facts、资料和关卡建立稳定 ID |
| 关卡模板 | `services.contracts.ScenarioTemplateV1` | 描述变量、NPC、行动、条件事件、结局规则和卷宗模板；条件与效果使用带 `kind` 的可判别结构，不允许任意代码表达式 |
| 游戏会话 | `services.contracts.GameSessionV1` | 固定课程包/关卡版本与 checksum，保存完整回合、状态快照、NPC 状态、节点、摘要、叙事观察和恢复信息 |
| 史官卷宗 | `services.contracts.DossierV1` | 保存关键回合、状态轨迹、主要代价、史实解释、知识节点与关系边，并引用原始 facts 和资料 |

`TurnV1`、`NpcStateV1` 是 `GameSessionV1` 的规范嵌套对象。四个顶层对象都使用固定 `schema_version`，禁止未知字段，拒绝 `NaN`/无穷数，时间字段要求带时区；ID 保持现有 2-64 位 ASCII 规则并区分大小写。Pydantic 的 `frozen` 只阻止顶层字段重新赋值，不能深冻结嵌套列表与字典；规则运行时必须复制输入、构造并重新校验新模型，禁止原位修改 sealed 制品或会话。课程包和关卡的 `status` 只表达 `draft|sealed` 制品状态，校验、审校、发布和回滚由 `BE-001` 的独立发布记录管理。

`RuntimeBundleV1` 是跨对象语义校验入口：除版本、ID 与 checksum 绑定外，还会从场景初始值按回合重算行动可用性、状态效果、自动事件、NPC 变化、节点迁移与结局优先级，并逐项核对 `state_changes`、`fact_refs`、`ruleset_hash` 和规则叙事，再核对卷宗结局、完整状态轨迹、会话时间线和关键选择原始输入。它用于拒绝“快照结构正确但不可能由规则产生”的伪造记录。`services/game_runtime/SituationEngineV1` 已能从 sealed 课程包和关卡文件启动、推进与重放会话；每次输入先通过 JSON 投影重建并深度校验，防止嵌套列表或字典被原位改写后绕过 Pydantic 验真。

V1 回放顺序固定为：校验当前节点与行动前置条件，先应用行动效果，再基于“行动后、事件前”的状态一次性筛选事件；事件按 `priority + event_id` 稳定排序后依次应用，`once=true` 的事件只触发一次，同回合事件之间不级联选取。数值效果逐条限制在变量或 NPC 的声明范围内，`rejected|failed` 回合不得产生状态、NPC 或事件效果。首次满足结局后不得继续追加回合，节点显式结局优先，否则选择满足条件且优先级最高的结局；命中结局的会话不能伪装成 `failed|abandoned`。会话不得超过 `max_turns`，`revision` 必须恒等于 `current_turn + 1`，active 恢复态的可用行动清单也必须能从当前状态复算。`client_action_id` 重试还必须携带产生原回合时的 `expected_revision`，不能在后续修订号上把旧动作误认成新重试。生成和验真共同调用 `services/contracts/rules_v1.py`，不得另设一套隐式顺序。

sealed 契约文件使用单一二进制句柄读取：先以 `fstat` 确认为普通文件并限制为 2 MiB，再做上限加一的有界读取，最后用 `lstat` 拒绝符号链接并核对打开对象与路径对象身份。JSON 仍拒绝重复 key、非法 UTF-8、未知字段和 checksum 篡改；不能恢复为“先检查路径、再按路径另读一次”的两阶段实现。

正常结果为导出 V1 运行契约与 `releases/v2` 联合发布契约的 schema/样板目录，且当前后端全量 170 项测试全部通过。生成器会清理这些受管目录中不再属于清单的旧 JSON，防止废弃 schema 或样板继续被下游误读。对外 JSON Schema 要求显式提供 `status`，防止省略默认值绕过生命周期分支。V1 draft 允许正文或关卡规则暂未写完，但不能携带封存元数据；sealed 才强制正文、变量、行动、结局、版本和 checksum 完整。checksum 只能对已经通过 Pydantic 校验的模型计算，不能直接签名未经规范化的原始字典。

`course_package_from_legacy()` 会保留旧 `LessonContentPackage` 的课程元数据、`draft|sealed`、版本、时间、saga/sandbox 素材和暂未解析引用；合法的旧画布 ID 原样保留，必须替换的 ID 写入 `compatibility.legacy_id_map`。旧 sealed 内容必须先通过源 checksum 校验，源 checksum 写入 `compatibility.source_checksum`，转换后的 V1 制品再生成自己的可复算 checksum，避免把被修改的旧文件重新签成可信制品。旧格式缺少逐条事实来源绑定时不会自行推测关系。大禹治水样板中的历史正文、facts、人物 persona 和解释均标有“教师待审”，只用于开发验收。

### 4.2 联合发布 V2 契约

`ARCH-002` 新增 `services/contracts/release_v2.py`，但不原地扩写已经落盘的 `course-release/v1`。`CourseReleaseManifestV1 | CourseReleaseManifestV2` 使用 `schema_version` 判别读取；现有 `course-release-pointer/v1` 继续作为唯一活动提交点，它可以固定 V1 或 V2 manifest 的路径与 checksum，不创建第二个“关卡活动指针”。

V2 的 `RuntimeArtifactDescriptorV1` 同时固定制品种类、Schema、稳定 ID、课程/课时、版本、checksum 与规范 POSIX 路径。课程包路径只能是 `runtime/v1/course-packages/{course_id}/{lesson_id}/vNNN-{checksum}.json`，关卡路径只能是 `runtime/v1/scenarios/{course_id}/{lesson_id}/{scenario_id}/vNNN-{checksum}.json`。`CourseReleaseItemV2` 把一个 sealed 课程源、一个内容寻址课程包和零到多个内容寻址关卡绑定为单课时快照；有场景时必须声明且只能引用本条目中的 primary 场景。manifest 还拒绝跨课时重复 `scenario_id`、重复制品路径、未排序条目、身份漂移和非法 lineage。

`calculate_release_metadata_checksum()`、`sign_release_metadata()` 与 `parse_signed_course_release_manifest()` 使用与现有发布元数据一致的规范 JSON SHA-256。这里的 checksum 用于意外损坏检测，不是抵御能够重写文件并重算整条链的数字签名；生产部署需把活动指针放入具备事务/CAS 与访问控制的可信存储。`content/examples/releases/v2/` 只是 development 契约夹具，文件存在不会令其进入 published 列表。

`BE-004` 已把内容工作流、课程读取与游戏目录接入 V2：新发布一律写 `CourseReleaseManifestV2`，V1 历史仍可读并会在下一次发布或回滚时转换为 V2；课程与正式关卡只由同一个 active pointer 同时生效。静态 `content/scenarios/catalog.v1.json` 被限制为 `audience=development`，不能自我晋升为正式内容；active V2 中的场景才投影为 `audience=published`。会话恢复把课程 ID、课时 ID、课程版本与 checksum、关卡 ID、版本与 checksum 一并传给历史查找，沿当前指针的可达 parent 链加载精确 bundle，不回退到“当前”或“最新”关卡。`FE-001` 已在该严格契约前增加服务器作者草稿、校验和封存接口，并在 `/admin/content` 接入不暴露 JSON 的关卡规则表单、效果预览、刷新恢复、原始字节导出及课程联合发布选择；编辑请求期间锁定表单并以编辑代次阻止旧响应覆盖新输入，切换草稿会保护未保存修改，token 变化会清空旧请求数据并只接纳最后一次响应。真实用户鉴权与隔离沿用后续身份任务。

ADR-0013 的学生侧发布身份交接已经实现：published 课时公开最小 `scenario_refs` 与唯一 primary，正式关卡启动必须携带 release、课程包和关卡的完整 pin，并从活动指针的可达历史精确验真；development catalog 保留仅按 ID 的兼容入口。published 会话的持久 envelope 保存原始 release ID、序号与 checksum，因此后续 release 即使原样复用同一组制品，也不能用同一 `client_request_id` 把旧会话重标记为新发布。旧 V1、内置和无关卡课时返回空绑定，不从全局目录猜测；前端“练”层只使用当前课时的 primary，先持久化请求 ID，再启动或刷新恢复并核对服务端完整身份。

`FE-002` 的前端合同集中在 `apps/web/src/pages/lesson/gameSessionReference.ts`：它从当前 published 课时与 primary 场景构造 release、课程包和关卡的联合身份，读取及回写 release-scoped 浏览器会话引用，并统一复验启动响应、完成态会话与 final 卷宗。“练”层完成后直接提供“整理卷宗”入口；“创”层使用原 `client_request_id + release_pin` 幂等重启并要求得到同一 `session_id`，再读取服务器复验后的卷宗，不能信任任意本地 session ID。`LessonCreate.tsx` 展示关键选择、主要代价、历史解释和追问，把知识节点与关系按课程 checksum 和稳定 ID 合并到现有画板，并在节点与关系 data 中保存 `session_id`、`dossier_id` 与 `dossier_checksum` 来源；重复导入不增殖节点，学生原节点与位置保持不变。无会话、未完成、release 漂移、卷宗损坏或网络错误只显示失败关闭状态，不伪造成果或覆盖画板。

## 10. 核心数据流

### 10.1 课程读取

```text
前端课程页
  -> GET /api/v1/courses
  -> courses.list_courses()
  -> 内置课程 + 每门课程 active V1/V2 release 指定的课程包

课时页
  -> GET /api/v1/courses/{course_id}/lessons/{lesson_id}
  -> courses.get_lesson(lesson_id)
  -> load_published_snapshots() 严格校验 pointer、manifest、旧 sealed、内容寻址课程包与关卡绑定
  -> 若存在已发布 lesson_id，返回正文、关键词、人物、地图点、资料与 release 身份
  -> 否则返回内置课程正文、关键词、人物、seed canvas、sandbox_id
  -> 任一已发布制品损坏时返回 503，不扫描目录猜测“最新版本”
```

### 10.2 saga 推演

```text
LessonPractice
  -> POST /practice/saga/start {lesson_id}
  -> saga.start(lesson_id)
  -> 开场、候选行动、persona、keywords

学生行动
  -> POST /practice/saga/{saga_id}/act {action}
  -> saga.act_stream()
  -> llm.stream_chat()
  -> text/plain 流式正文 + [META] JSON
```

saga 模板包含 `facts`、`era`、`setting`、`persona`、`opening`、`initial_choices`、`keywords`。`step >= 5` 倾向收束，`step >= 7` 必须收束。

### 10.3 sandbox 决策沙盘与 V1 局势核心

legacy 接口保持兼容：

```text
GET /practice/sandbox/{sid}
  -> scenario、start node、init_state

POST /practice/sandbox/{sid}/step
  -> sandbox.step()
  -> 下一节点、feedback、新 state
```

legacy `sandbox.step()` 信任客户端传入 state，只供旧页面兼容，禁止用于 V1 会话。V1 核心调用链为：

```text
SituationEngineV1.from_files(course_path, scenario_path)
  -> UTF-8 JSON、重复 key、sealed 状态、checksum 与 RuntimeBundle 跨引用校验
  -> start_session(...)
  -> 初始变量、NPC、节点、可用行动与精确制品身份

apply_action(session, RuntimeCommandV1)
  -> 复验完整历史和 expected_revision
  -> rules_v1.evaluate_rule_action()
  -> 行动效果 -> 事件筛选/执行 -> 节点迁移 -> 结局裁定
  -> 生成 TurnV1 与新 GameSessionV1
  -> RuntimeBundleV1 再次确定性回放验真
```

纯规则核心可按 `action_id`、label 或 alias 确定性解析行动，本身不会用模糊字符串或 LLM 猜测行动。API 协调层中，固定按钮只提交 `action_id`，服务端从固定关卡制品取得教师标题并写入回合；自由文本则先由 `ActionClassifierV1` 映射到当前可用行动，再以 `action_source=free_input` 进入同一规则核心。相同 `client_action_id` 和相同输入返回原结果，不同输入复用该 ID 会冲突；`expected_revision` 防止并发覆盖。引擎不在原模型上修改嵌套字典或列表。达到 `max_turns` 却没有模板结局、或未到上限但没有可用行动时，关闭为可解释的 `failed` 状态。

V1 API 调用链：

```text
GET  /api/v1/practice/game/scenarios
  -> 合并 catalog.v1.json 的 active development 条目与 active V2 release 的 published 条目
  -> 返回固定版本/checksum、课程身份、audience 与关卡摘要

POST /api/v1/practice/game/sessions {scenario_id, client_request_id, release_pin?}
  -> published 场景必须提交 release ID/序号/checksum、课程/课时、课程版本/checksum 与关卡版本/checksum；development 场景可省略 pin
  -> 服务端只沿当前活动指针的可达 V2 parent 历史查找完全匹配的发布，不可达、错绑或损坏制品均不创建会话
  -> client_request_id 必填；相同用户、release 与七段制品身份重试返回同一会话，任一身份变化返回 duplicate_start_conflict
  -> published 摘要回显服务端验真的 release 身份，调用方同时核对 session 中的七段制品身份

GET  /api/v1/practice/game/sessions/{session_id}
  -> 从 SQLite 读取带 checksum 的完整会话
  -> 按课程/课时/课程版本与 checksum、关卡 ID/版本与 checksum 从静态制品或可达 release 历史精确加载并重建 RuntimeBundleV1 验真

POST /api/v1/practice/game/sessions/{session_id}/turns
  -> 固定行动只接收 client_action_id、action_id、expected_revision
  -> raw_input、action_source、classification_confidence、state/current_turn/ending 等客户端权威声明因 extra=forbid 被拒绝
  -> 服务端从固定关卡制品读取行动标题，来源固定为 fixed，置信度固定为 1.0
  -> 先生成纯规则候选，再在状态锁和数据库事务外请求受约束叙事；返回后复核原 revision，并把 Turn、叙事证据和完成态卷宗一次 CAS 提交

POST /api/v1/practice/game/sessions/{session_id}/free-input
  -> 只接收 client_action_id、raw_input、expected_revision，拒绝客户端候选 action_id 与分类元数据
  -> 精确 ID/标题/alias 免模型；其余输入只能由结构化分类器映射到当次可用行动
  -> advanced 才产生 Turn 并使 revision + 1；clarification_required/rejected/provider_unavailable 返回安全提示和可用行动但不写会话
  -> 分类在状态锁与数据库事务外执行，返回后重新读取 revision；期间发生其他回合则返回 revision_conflict，不在新状态上自动重试分类
  -> matched 分支同样先结算纯规则候选，再在锁外生成叙事并复核 revision；叙事失败不撤销合法行动，而是以稳定原因码和逐字规则文本完成同一次 CAS

GET  /api/v1/practice/game/sessions/{session_id}/replay
  -> 从固定课程/关卡制品重新推导规则状态、basis、history、summary 与卷宗引用
  -> 复用通过证据校验的持久叙事，不调用分类器、叙事器或外部供应商

GET  /api/v1/practice/game/sessions/{session_id}/dossier
  -> 只读取并复验已物化卷宗；不会因 GET 产生写入

POST /api/v1/practice/game/sessions/{session_id}/dossier
  -> 仅为旧完成态会话显式幂等补建卷宗

GET  /api/v1/practice/game/sessions/{session_id}/summary
  -> 返回教师可读的会话、选择、轨迹、facts、资料与卷宗身份摘要
```

场景路径相对 `CHRONO_CONTENT_ROOT`，必须是规范 POSIX JSON 路径；仓库不扫描目录猜测关卡。静态 catalog 只允许 `audience=development`，正式关卡只来自 active V2 release；同一 `scenario_id` 正式发布后，active published 投影覆盖 development 列表项，旧开发会话仍按完整身份从静态制品恢复。catalog、pointer、manifest 和制品都使用严格读取与完整身份校验，拒绝逃逸、符号链接、重复 key、路径身份或 checksum 漂移。同一课程包可供多个关卡复用，但路径对应的课程 ID、课时 ID、版本与 checksum 必须完全一致。

API 的 `session_storage=sqlite-json` 表示完整 `GameSessionV1`（含 Turns、状态快照、NPC、结局）是唯一规则状态事实源，`game_sessions` 表只保存 `session_id / data / updated_at`。`data` 使用规范 JSON、4 MiB 上限和会话级 SHA-256 envelope；新写入统一使用 `persisted-game-session/v2`，published 会话还固定 release ID、序号与 checksum。旧 `persisted-game-session/v1` 必须先对原始 JSON 中尚未补默认字段的 `session/release_identity` 按旧算法核对 checksum，再映射为 `ai_evidence_version=0`；下一次成功 CAS 或卷宗挂接才原子写成 V2，并原样保留 release identity。V1 不允许伪装携带新证据字段。release 元数据只约束启动来源和幂等，不参与规则结算。读取先拒绝损坏 JSON、重复 key、身份/checksum 不一致，再按会话固定的关卡版本与 checksum 加载原制品，并用 `RuntimeBundleV1` 重推规则和证据 basis。写回必须使 revision 恰好增加一，并用“主键 + 原始整段 data”执行原子 compare-and-swap；同进程 `RLock` 降低冲突，其他进程或连接仍由数据库 CAS 裁决。分类与叙事调用都位于状态锁和数据库事务外；叙事前只形成不可见的规则候选，叙事返回后再次读取原 revision，未漂移时才把规则状态、展示文本、类型化证据及可选完成态卷宗一次 CAS 提交。自由输入同一已提交请求跨服务竞争只保留一个赢家，即使两次模型分类或叙事不同也恢复数据库中的既有回合；其他陈旧动作返回 revision 冲突，旧叙事不会套到新状态。当前不持久化澄清、拒绝或供应商失败的 attempt receipt，也不提供模型请求租约，因此零写入结果或 CAS 决胜前的竞争请求可能重复调用供应商；该边界影响调用成本，不会重复推进状态。应用 lifespan 关闭后 SQLite 文件保留，重启可继续游玩；开发期仍只有单一配置用户，尚无生产级用户隔离。

`game_dossiers` 表以相同 envelope 方式保存完整 `DossierV1`，单记录上限为 2 MiB。最终回合与卷宗在同一数据库事务中完成，会话不会先进入完成态再留下悬空 `dossier_id`；旧完成态会话只能通过显式 POST 在同一事务中补建并挂接。卷宗 ID、标题、选择、状态轨迹、代价、解释、facts、资料、反思问题和允许的知识节点均由固定场景、课程字段及真实回合确定性派生；没有封存关系契约时不编造知识边，也不代写学生或教师反思。读取时除 checksum 和 `RuntimeBundleV1` 外还会重新派生并逐字段比对，因此“修改文本后重算 checksum”仍会失败关闭。

这里的 `final` 只表示一次会话的不可变技术制品已经生成，不等同于内容通过历史审校或进入正式发布。只有 catalog 中明确标记为 `audience=published` 且走完课程/关卡联合发布流程的制品，才可作为正式教学版本；当前两份样板仍只用于开发验收。

### 10.5 canvas 画板

```text
GET /practice/canvas/{lesson_id}
PUT /practice/canvas/{lesson_id}
POST /practice/canvas/generate
```

画板保存在 SQLite KV：namespace=`canvas`，key=`lesson_id`。

GET 返回 `schema_version="canvas/v1"`、`found`、`revision`、`nodes` 和 `edges`。未创建画板是 `found=false, revision=0`，与教师或学生明确保存的空画板区分；旧 `{nodes, edges}` 记录按 revision 1 读取，并在下一次成功保存时迁移为版本化信封。PUT 必须携带 `expected_revision`，服务端通过 `kv_compare_and_set()` 对原始完整记录执行原子比较交换，成功后 revision 加一；同一快照的并发写入只有一个成功，陈旧写返回 `409 / canvas_revision_conflict` 且不覆盖新图。损坏或未知结构的存储记录返回 `500 / canvas_integrity_error` 并失败关闭，不以种子节点覆盖原记录。

`LessonCreate.tsx` 串行化自动保存请求并记录当前 lesson、加载代次、编辑代次与服务器 revision；非用户触发的 React Flow 尺寸或选择变化不标记 dirty，拖动、增删、连边、AI 扩充和卷宗导入才触发 debounce 保存。遇到 `409` 后画板进入只读冲突态，只允许重新载入最新版本，不提供盲目覆盖。React Flow 仅在当前“创”层可见且父容器已测得非零尺寸后挂载，避免隐藏页签或响应式切换产生零尺寸实例。

## 12. LLM 适配层

兼容流式入口：

```python
stream_chat(messages, provider=None, model=None)
```

严格结构化入口：

```python
result = await complete_json(messages, ResponseModel, model=None)
# 或注入 transport/fake 进行离线测试
result = await StructuredLLMAdapter(...).complete(messages, ResponseModel)
```

| provider | 说明 |
| --- | --- |
| `mock` | 离线兜底，保障课堂主流程不中断 |
| `deepseek` | OpenAI 兼容协议，支持 `deepseek-v4-flash` 与 `deepseek-v4-pro` |

模型分工：

- saga：速度优先，默认 `deepseek-v4-flash`。
- ask：准确度优先，显式 `deepseek-v4-pro`。
- 异常或无 API Key：回落 mock。

规则：

- 业务层不得直接拼 LLM HTTP。
- LLM 不决定史实真值；当前史实边界来自课程 `facts`、`source_refs` 和教师审校，RAG 尚未实现。
- mock 回退是课堂可靠性设计，不是临时调试残留。
- `stream_chat()` 保持 legacy saga/ask 兼容；HTTP 错误、网络异常和空流只返回稳定离线提示与 mock 文本，不向学生暴露供应商 body 或异常原文。
- `complete_json()` 不伪造通用 mock 结构。provider 未配置、超时、限流、HTTP 失败、超长、截断、重复 key、非对象 JSON 或 Pydantic 校验失败均抛出只含稳定 `LLMFailureCode` 的 `StructuredLLMError`，由分类/叙事业务层决定“不推进回合”或“使用规则文本”。
- `StructuredLLMAdapter` 自动附加响应模型 JSON Schema，启用 `response_format=json_object`，禁用 V4 thinking，分块读取并在配置上限立即中止；规范化输出只保存 SHA-256 checksum，不保留原始供应商响应。

结构化配置位于 `apps/api/settings.py` 与 `apps/api/.env.example`：

| 环境变量 | 默认值 | 边界 |
| --- | --- | --- |
| `CHRONO_LLM_STRUCTURED_TIMEOUT_SECONDS` | `12` | `1-60` 秒；超时转换为 `provider_timeout` |
| `CHRONO_LLM_STRUCTURED_MAX_TOKENS` | `512` | `32-4096`；调用方还可在更小范围覆盖 |
| `CHRONO_LLM_STRUCTURED_MAX_RESPONSE_BYTES` | `32768` | `1024-262144` 字节；按响应流累计限制 |

结构化适配器的离线验证位于 `tests/test_llm_adapter.py`。测试使用 `httpx.MockTransport`，不访问真实模型，也不读取或保存真实 API key。

### 12.1 服务端行动归类器

`services/ai/ActionClassifierV1` 是自由文本进入规则引擎前的纯归类服务：

```python
classification = await ActionClassifierV1().classify(engine, session, raw_input)
```

- 输入先按 `PlayerInput` 做严格长度与空白校验；会话不是 active、没有可用行动或输入非法时直接拒绝。
- 稳定 `action_id`、教师标题和 alias 先由 `SituationEngineV1.resolve_action_id()` 精确解析，命中当前可用行动时不调用模型；精确命中但当前不可用时失败关闭。
- 只有精确解析失败且存在与当前关卡/行动相关的已审 facts 时才调用结构化分类器。模型上下文不包含 `teacher_note`、资料路径、密钥、规则效果或完整会话状态。
- `ActionClassificationV1` 只能表达当前行动匹配、需要澄清、拒绝或供应商不可用；匹配的 `action_id` 必须属于服务端当次计算的 `available_action_ids`，LLM 来源还必须带 provider、model 与规范输出 checksum。
- 低置信度、未知行动、提示注入、越时代、事实冲突、输出异常与供应商异常都不会修改传入会话。归类器本身不调用 `apply_action()`，规则引擎仍是状态、事件、NPC 和结局的唯一权威。

`GameRuntimeService.apply_free_input()` 已把纯归类服务接入独立 API：模型调用不占状态锁，返回后重新核对相同 revision，并只把 `matched` 结果交给规则引擎；澄清、拒绝和分类供应商故障均以 `FreeInputResultV1` 零写入返回。固定行动 API 使用异步 `submit_fixed_action()` 生成服务端标题、来源与置信度；同步 `apply_fixed_action()` 只保留给纯规则兼容与内部测试，客户端不能提交这些权威字段。

`HistoricalNarratorV1` 使用 `NarratorModelOutputV1`，模型只能返回 1—1200 字展示文本和不超过 32 个实际使用的 fact/source ID，未知字段、重复/越界引用、超长文本、空/截断响应或供应商故障均回退为逐字 `render_rule_narrative()`。上下文只包含固定课程/关卡身份、已结算行动、状态差、NPC 变化、触发事件、结局投影、已审 facts/source ID 以及关卡 persona/boundaries；不发送学生原文、教师备注、资料路径、密钥、规则 effects 或既有模型历史。带 `pending` 资料或“教师待审”标记的 facts 不会触发叙事供应商。

新服务会话使用 `ai_evidence_version=1`。每个 applied Turn 同时保存严格 `ActionClassificationEvidenceV1` 与 `NarrativeEvidenceV1`：前者固定分类 policy、回合前可用行动、已审 fact 白名单、provider/model、模型输出 checksum 与规则快照 basis；后者固定同一次规则结算 basis、允许及实际使用的 fact/source ID、文本 checksum、provider/model 或稳定 fallback 原因。`SituationEngineV1.with_narrative()` 会重新计算规则结果与叙事 basis，只替换 Turn/history 中的展示文本，再用 `RuntimeBundleV1` 复验状态、NPC、事件、结局、两层 basis、`history`、`summary` 和卷宗 consequence。旧版本 0 会话只允许可重算的 `rules` 叙事，不补造历史证据；`replay_session()` 直接返回验真的持久叙事，不调用分类器、叙事器或供应商。

`PublishedGamePractice` 已接入 `gameFreeInput()`：学生可在固定行动之外输入不超过 400 字的自拟行动，Enter 提交、Shift+Enter 换行；请求期间固定、自由和“重新开始”控件共同锁定，避免旧回合结果覆盖新 session。`advanced` 必须返回完整、同 release 身份的会话才会替换当前历史并清空输入；澄清、拒绝和供应商不可用只显示可关闭提示，保留原输入且不伪造回合。网络或并发错误会重新读取服务器权威会话，刷新页面继续恢复同一 session；显式重新开始才创建新 session，并清空旧输入和提示。隔离 published 样板已完成桌面与 `390×844` 浏览器验收：精确标题自由输入推进至 revision 1，供应商不可用保持 revision 1，刷新恢复历史，重新开始回到 revision 0，移动端无横向溢出。该界面不等同于完整 AI 助教或 RAG 已上线。
