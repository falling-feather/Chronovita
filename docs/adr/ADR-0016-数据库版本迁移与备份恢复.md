# ADR-0016 数据库版本、迁移与备份恢复

- 状态：接受
- 日期：2026-07-16
- 目标版本：V0.9.x
- 决策人：核心开发组 / 数据与数据库组

## 背景

Chronovita 已有 `kv`、游戏会话/卷宗和账号/会话/审计三组 SQLAlchemy Core 表，但它们分别在 `services/persistence/db.py`、`services/game_runtime/store.py` 和 `services/auth/store.py` 中调用 `create_all()`。这种方式适合早期单机开发，无法回答数据库当前处于哪个版本、从哪个旧版本升级、结构是否被手工改坏、失败后是否完整回滚，也无法为备份恢复或 Postgres 部署提供可验证边界。

V0.9.x 仍需保留教师电脑上的 SQLite 离线体验，同时让 accounts 模式具备明确的数据库生命周期。正式课程文件、人物、关键词和资料不存入本轮新关系表，也不属于本决策的迁移范围。

## 决策

### 1. 单一 schema 管理器先于业务服务启动

`services/persistence/` 负责创建 Engine、执行或校验登记迁移，并在成功后才把 Engine 交给身份、学生资产扫描、内容和游戏服务。应用启动顺序固定为：

```text
解析数据库配置
  -> 建立受支持 dialect 的 Engine
  -> 取得迁移锁
  -> 校验迁移账本和真实表结构
  -> 按策略执行登记的安全迁移或拒绝启动
  -> 配置身份服务
  -> 检查未映射学生资产
  -> 配置内容与游戏服务
```

应用生命周期不再依靠各 Store 的 `create_all()` 猜测缺表。测试夹具也必须调用同一 schema 管理器，或显式建立自己要验证的损坏旧库；不得保留只在测试环境成立的第二套建表真相。

### 2. 迁移账本只追加且版本连续

数据库使用 `chronovita_schema_migrations` 保存已提交迁移，最低字段为：

| 字段 | 含义 |
| --- | --- |
| `version` | 从 1 开始且无缺口的整数主键 |
| `migration_id` | 稳定、唯一、可读的迁移标识 |
| `contract_checksum` | 迁移声明中表、列、主键、索引和不变量的规范摘要 |
| `applied_at` | UTC 提交时间 |
| `app_version` | 首次登记该迁移的 Chronovita 版本 |

已发布迁移不可改写、重排或复用版本号。启动发现账本版本高于当前代码、版本缺口、重复 ID、checksum 不一致或真实结构偏离声明时一律失败关闭，不自动降级、不删除列、不重建未知数据。

### 3. 当前历史按三段可认领 schema 登记

首轮注册表按真实引入顺序建立：

| 版本 | 迁移 ID | 管理对象 |
| --- | --- | --- |
| 1 | `core-kv-v1` | `kv` |
| 2 | `game-runtime-v1` | `game_sessions`、`game_dossiers` |
| 3 | `identity-audit-v1` | `auth_users`、`auth_sessions`、`auth_audit_head`、`auth_audit_events` 及审计头初始不变量 |

没有迁移账本的旧库只能走严格认领：

1. 空库按 1 至最新版本顺序创建。
2. 一段迁移管理的表全部存在且结构逐项一致时，只登记该历史版本，不改业务数据。
3. 一段迁移管理的表全部不存在时，执行该登记迁移。
4. 同一段只存在部分表、出现未知业务表、列/主键/索引漂移或审计头与事件不一致时拒绝认领。

该规则使 V0.8.x 的 `kv + game` 数据库可以认领 1、2 并执行 3，使当前 V0.9.5 数据库可以认领 1 至 3；它不会把任意 SQLite 文件或手工拼出的半套表冒充成 Chronovita 数据库。

### 4. 迁移必须原子、串行、可重复

每段迁移在一个事务中完成 DDL、数据不变量修复和账本追加。SQLite 使用排他写入语义避免两个启动进程同时认领；Postgres 先取得会话级 advisory lock 并结束锁获取事务，再开启新的 `REPEATABLE READ` 迁移事务，提交或回滚后显式解锁。等待者因此只会在前一迁移提交后建立快照，不会拿着等待前的旧视图重复建表。只读 schema/审计复验也使用 `REPEATABLE READ`，使一次检查中的账本、表合同、审计头和事件来自一致快照。并发者只能看到完整旧版本或完整新版本。

迁移函数必须幂等校验，但不能以 `IF NOT EXISTS` 掩盖结构不一致。进程中断、账本写入失败和不变量失败均不得留下已登记的半迁移。破坏性迁移、不可逆数据重写和需要教师确认的业务映射不标记为启动安全迁移，必须由独立命令执行；V0.9.5 的学生资产迁移继续保持独立回执，不混入 schema 账本。

### 5. KV 写入必须使用数据库原子语义

`kv_set()` 在 SQLite 和 PostgreSQL 上都使用单条 `INSERT ... ON CONFLICT DO UPDATE`，不得先查询再决定插入或更新。`kv_compare_and_set()` 在 SQLite 上先取得立即写锁，在 PostgreSQL 上锁定已有目标行，再按解析后的规范 JSON 值比较并更新；旧记录的空白、对象键顺序或历史序列化格式不能制造虚假冲突。调用方必须传递独立的 presence 位区分“不存在”和“存在且值为 JSON null”，旧 `expected=None` 仅作为“不存在”的兼容含义保留。

### 5. 启动策略分为安全应用和只校验

数据库迁移策略固定为：

| 模式 | 行为 |
| --- | --- |
| `apply-safe` | 应用已登记且声明为启动安全的待执行迁移，然后复验最新结构 |
| `validate` | 只接受已经位于当前最新版本且结构一致的数据库；存在待执行迁移即拒绝启动 |

本地离线和自动化测试可默认 `apply-safe`。生产部署由 `OPS-001` 强制使用显式迁移命令后再以 `validate` 启动。无论哪种模式，未知、超前、倒退、缺口或漂移都不能降级为 `create_all()`。

### 6. 数据库连接配置不再绑定文件路径

`CHRONO_DATABASE_URL` 非空时优先于兼容项 `CHRONO_SQLITE_PATH`。首轮仅接受 SQLAlchemy 的 `sqlite` 与 `postgresql` dialect，其他 scheme 明确拒绝；日志和错误不得输出数据库密码。

SQLite 是 V0.9.x 离线模式与自动化测试的完整支持后端。Postgres 使用同一迁移声明、稳定主键、显式约束和事务语义，不引入 SQLite 专属业务判断。V0.9.14 已增加显式连接池/连接超时、production `sslmode=verify-full` 配置门禁、环境变量式 status/migrate 命令，以及 PostgreSQL 16.14 基础服务矩阵；V0.9.15 再把审计头追加改为数据库行锁，并在并发写入期间复验链和 schema 一致快照。CI 内部数据库不启用 TLS；最后管理员/bootstrap、KV 竞争、真实证书握手、故障转移、`pg_dump` 调度和部署凭据继续由 `OPS-001`、`QA-001` 接续，在这些边界通过前不得宣称 Postgres 生产部署完成。

### 7. SQLite 备份有清单，恢复先验证后替换

显式数据库命令提供 `status`、`migrate`、`backup`、`verify-backup` 和 `restore`。SQLite 备份使用官方 backup API 生成一致快照，先写同目录临时文件，执行 `quick_check`、schema 校验和文件 SHA-256 后再原子落盘，同时生成 `chronovita-backup-manifest/v1` JSON 清单。清单最低记录 backup ID、创建时间、schema 版本、文件大小和 checksum，不记录密码、token、学生正文或数据库 URL。

恢复必须在 API 停止时进行。默认只恢复到不存在的目标；覆盖现有数据库必须显式确认并先生成可验证的恢复前安全副本。恢复流程先验证清单、文件 checksum、SQLite `quick_check` 和 schema，再同目录原子替换，替换后重新打开复验。损坏、超前版本、清单不匹配或路径指向同一文件时拒绝操作。

Postgres 备份恢复不伪装成文件复制；后续只通过数据库原生工具与 OPS 管理的凭据执行。

### 8. 稳定失败语义与可观察状态

schema 层异常使用稳定代码区分：配置不支持、迁移待执行、版本超前、历史缺口、迁移 checksum 不符、结构漂移、迁移锁冲突、完整性检查失败和备份清单不符。API 启动失败不得吞掉根因，也不得在错误后继续提供健康或业务接口。

`status` 输出当前版本、最新支持版本、待执行迁移、dialect 和结构是否有效，不输出连接密码或业务数据。SQLite 使用 `--database` 文件参数；PostgreSQL 的 `status|migrate` 只接受 `--database-url-env` 指定的环境变量名，空库创建还要求 `migrate --initialize`，URL 不进入命令行或结构化输出。`backup|verify-backup|restore` 仍只支持 SQLite；`healthz/readyz` 对 schema 状态的公开投影由 `OPS-001` 接入。

## 验收反例

- 空库、真实 V0.8.x 结构和 V0.9.5 结构均可到达同一最新 schema，重复迁移不产生新写入。
- 只有一张 auth 表、手改列、错误主键、迁移账本缺号、重写 checksum 或高于代码版本的数据库全部拒绝启动。
- 两个进程并发迁移只产生一套连续账本；故障注入后不存在半表或提前登记版本。
- 备份文件与清单可在新路径恢复并通过业务读取；任一字节篡改、错误清单或超前 schema 均拒绝恢复。
- 数据库 URL、异常和日志中不出现密码；不支持 dialect 不回退到 SQLite。
- Postgres DDL 编译不出现 SQLite 专属类型或文件路径语义；PostgreSQL 16 基础服务矩阵验证双 Engine 并发迁移、连续账本、真实反射和 API 串行烟测，同时明确不以无 TLS 单实例容器替代多 worker、证书、故障转移和原生备份验收。

## 后果

正面影响：数据库升级具备明确版本、可复验历史和失败边界；旧库升级、备份恢复、生产启动与未来 Postgres 接入共享一套事实来源；业务 Store 不再分别猜测表结构。

代价与限制：所有直接构造 Store 的测试和脚本需要先接入 schema 管理器；严格结构认领会拒绝过去可以被 `create_all()` 悄悄补齐的半损坏数据库；SQLite 与 Postgres 的锁和备份实现仍需 dialect 适配，真实 Postgres 上线还依赖 OPS/QA 服务矩阵。
