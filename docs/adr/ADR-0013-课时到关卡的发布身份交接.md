# ADR-0013 课时到关卡的发布身份交接

- 状态：接受
- 日期：2026-07-15
- 决策人：核心开发组
- 计划版本：V0.8.x（具体补丁版本待项目负责人收口确认）

## 背景

`CourseReleaseManifestV2` 已把课程包和关卡模板封装为同一不可变 release，持久会话也会固定课程/课时/课程版本与 checksum、关卡 ID/版本与 checksum。但学生侧尚未完整传递这份身份：课时接口只返回课程 release 身份，没有公开已绑定的 `scenario_refs`；`POST /practice/game/sessions` 只接收 `scenario_id`，服务端会重新查找调用时的 active 场景。

因此，学生在 release A 打开课时、教师随后发布 release B、学生再点击“进入抉择”时，可能启动同 ID 的 B 版关卡。启动幂等判断目前也只比较用户与 `scenario_id`，同一请求 ID 在关卡升版后可能错误返回旧会话。这个窗口会破坏“看见的课程内容、进入的关卡、AI 使用的 facts 属于同一快照”的约束。

## 决策

### 1. 课时响应公开最小关卡绑定

published 课时响应继续返回现有 `release_id`、`release_no`、`release_checksum`、`content_version` 与 `content_checksum`，并新增：

- `scenario_refs[]`：只含 `scenario_id`、`scenario_version`、`checksum`、`primary`。
- `primary_scenario_id`：无关卡时为 `null`，有绑定时指向唯一 primary。

不向学生返回 sealed/runtime 路径、教师备注或管理元数据。旧 V1 release、内置课程和未绑定关卡的课时返回空列表与 `null`，不猜测 catalog 中名称相似的关卡。

### 2. 正式启动必须携带 release pin

`GameStartRequest` 保留 `scenario_id + client_request_id`，并增加可选严格对象 `release_pin`：

```text
release_id + release_no + release_checksum
course_id + lesson_id
course_content_version + course_checksum
scenario_version + scenario_checksum
```

- `audience=development` 的静态 catalog 兼容旧调用，可省略 `release_pin`。
- `audience=published` 不接受仅凭 `scenario_id` 的启动；必须提交课时响应形成的完整 pin。
- pin 只是一项待验声明。服务端必须从该课程当前 active pointer 出发，沿可达 parent release 链找到 release ID/序号/checksum 完全一致的 V2 manifest，再核对课时条目、课程制品描述符和已绑定场景描述符。
- 任一字段不一致、release 不可达、课时未绑定该场景、制品损坏或只存在同 ID 的“当前版本”时均失败关闭，不回退到 active/latest 场景。
- release A 在后续发布或回滚后仍位于可达历史时，持有 A pin 的已打开页面可以启动 A 的精确 bundle；这与既有旧会话恢复语义一致。

### 3. 启动结果回显已验证身份

`ScenarioSummaryV1` 对 published 场景回显已验证的 `release_id`、`release_no` 与 `release_checksum`；development 场景保持三者为空。响应中的 session 已含七段课程/关卡制品身份，调用方应核对其与请求 pin 一致。

release 身份用于证明启动来源，规则行为仍由七段制品身份决定。相同课程包与关卡制品被后续 release 原样复用时，不扩写 `GameSessionV1` 或复制一套状态；重启回放继续按七段身份加载并重放。

### 4. 幂等比较使用完整运行身份

`client_request_id` 仍与服务端用户组成确定性 session ID。重复创建只在以下内容全部一致时返回原会话：

- 用户 ID。
- 课程 ID、课时 ID、课程版本与 checksum。
- 关卡 ID、关卡版本与 checksum。

同一请求 ID 改用其他 release、其他课时或同 ID 的其他关卡版本必须返回 `duplicate_start_conflict`，不能因 `scenario_id` 相同而复用旧结果。

### 5. 前端只从当前课时选择默认关卡

课时“练”层默认选择 `primary=true` 的绑定，不再通过全局场景列表或硬编码 sandbox/saga 名称猜测正式关卡。没有 primary 时显示稳定的“本课时尚未发布互动关卡”状态；development 入口仍可供开发验收，但不能伪装成正式课程绑定。

## 验收

- V2 published 课时返回完整 release 身份、关卡 refs 和唯一 primary，V1/内置/无绑定课时保持空值兼容。
- 精确 pin 可启动正确 published bundle；缺 pin、错 release checksum、错课程/课时、错场景版本或未绑定场景均不创建会话。
- 获取课时后发布新版本，旧 pin 仍启动旧可达制品，新课时响应启动新制品；两者不会互换。
- 同一 `client_request_id` 与完整相同身份幂等，任一制品身份不同稳定冲突。
- 启动响应、持久会话与重放的课程/关卡版本及 checksum 一致；制品或 manifest 篡改继续返回稳定失败。

## 后果

正面：

- “内容读取 -> 进入练习 -> AI facts 上下文”共享同一发布快照，消除页面打开与点击启动之间的 active 漂移。
- 保留 development catalog 和既有会话格式，改动集中在学生投影、启动合同和发布历史解析。
- 完整 pin 可直接用于前端恢复、错误提示和端到端验收，不依赖猜测“最新版本”。

负面：

- published 启动请求字段增多，前端必须把课时响应作为唯一来源并处理无绑定状态。
- 旧 pin 依赖 release 历史仍可达；未来若引入历史清理，必须先定义会话保留期与归档策略。
- 该决策不解决真实学生身份、多设备会话列表或课程分配权限，仍沿用后续身份任务。

## 被拒绝的方案

- **只传 `scenario_id` 并在点击时读取 active**：存在 release 漂移，拒绝。
- **只传 scenario 版本/checksum，不传课程和 release 身份**：不能证明关卡与学生看到的课时属于同一发布，拒绝。
- **把完整场景 JSON 交给浏览器再回传**：扩大篡改面并泄露规则细节，拒绝。
- **把 release ID 写进新的会话状态副本**：七段制品身份已足以确定规则行为，避免无必要迁移与双重真相。
